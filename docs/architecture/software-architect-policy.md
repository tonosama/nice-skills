---

## 1. 目的

次の転換を、コストを抑えつつ段階的に進める。

1. **実行基盤**: オンプレ → クラウド
2. **アプリ構造**: チャンク型 → マイクロサービス＋軽量な横展開
3. **データ基盤**: Oracle Exadata 依存 → 段階的に脱 Oracle（残す理由は都度検証）
4. **パッケージと業務の関係**: 「パッケージに業務を無理に合わせる」状態から、**変えたい業務を変えられる構造**へ寄せる

方針の役割は全体地図を完成させることではない。  
**迷ったときの判断軸**と、**最初の一歩（パイロット）を安全に切るための最低条件**を共有することである。

---

## 2. 現状認識（合意＋仮説）

| 認識 | 確度 | 扱い |
|---|---|---|
| オンプレ中心 | 高 | 前提として使う |
| 規模が大きく、全面現状分析はコスパが悪い | 高 | **やらない**（下記「最低限調査」に限定） |
| パッケージを改良し、業務をパッケージ側に合わせている | 高 | 移行設計の中心リスクとして扱う |
| チャンク型 | 中 | 定義の深掘りはしない。パイロット境界だけ見る |
| Exadata／Oracle が中核 | 高 | 依存の「種類」だけ最低限見る（全スキーマ棚卸しはしない） |
| Oracle 残置メリットは未整理 | 高 | 残すなら根拠ゲート。なければ寄せない |

---

## 3. 調査についての判断（結論）

**全面の現状分析はしない、でよい。**  
ただし「何も調べないで大規模移行を決める」は別問題で、失敗コストが大きい。

取るべきは **最低限調査（Minimum Discovery）**:

- 目的は「全体を理解する」ではなく **パイロットを切る／切らないを決める**
- 時間を区切る（目安: 短時間のヒアリング数回＋既存資料の拾い読み）
- 分からないことは「不明のまま進み、パイロットで学ぶ」と明示する
- 全体地図はパイロット成功後に、必要な範囲だけ広げる

詳細項目は [discovery-checklist.md](./discovery-checklist.md)（必須はごく少数）。

---

## 4. 最低限やるべきこと

パイロット着手前に揃えるのは、次の **6 点だけ**とする。

| # | 最低限 | 十分の目安 | やらない例 |
|---|---|---|---|
| M1 | **パッケージの境界** | 標準機能／改造／アドオンのざっくり比率と、改造が集中する箇所 | 全カスタムのコードレビュー |
| M2 | **業務を合わせている痛み** | 「本来やりたいがパッケージ都合で諦めた／歪めた」業務を 3〜5 件 | 全業務フローの As-Is 文書化 |
| M3 | **切れそうな薄皮** | パッケージ外に出せそうな領域を 1〜2 候補 | 全ドメインのサービス分割設計 |
| M4 | **Oracle／Exadata の縛り方** | ライセンス感＋固有機能依存の有無（ある／ない／不明） | 全テーブル・全 PL/SQL 棚卸し |
| M5 | **落とさない制約** | 止めてはいけないもの、バッチ窓、個人情報などの「線」 | 詳細 RTO／RPO の精密定義 |
| M6 | **成功の定義（小さく）** | パイロットで何が証明できれば次に進むか | 全社 KPI の再設計 |

これ以外は **後回し可**。必要になったとき、そのスライスだけで調べる。

---

## 5. パッケージ前提の設計原則

現状は「パッケージ改良 ＋ 業務をパッケージに合わせる」構図である。  
ここを無視したマイクロサービス化は、改造コストをクラウドに持ち運ぶだけになりやすい。

| # | 原則 | 意味 |
|---|---|---|
| K1 | **パッケージ核は当面残してよい** | いきなりパッケージ置換を必須にしない |
| K2 | **新しい差分は外に出す** | 追加改造をパッケージ内に増やさず、外側サービスへ |
| K3 | **業務都合をパッケージ標準にねじ込まない** | 歪みが大きい要件は、外出し or 将来置換候補として記録する |
| K4 | **改造は負債として見える化** | 「何を・なぜ・ベンダー升级で壊れるか」を短く残す |
| K5 | **合わせる／合わせないの基準を持つ** | 標準に寄せる価値（升级・保守）と、業務固有の価値を比較して決める |

### パッケージ戦略の三択（今は決め切り不要）

| 選択肢 | 向くとき | リスク |
|---|---|---|
| A. 核はパッケージ継続、周辺をサービス化 | 標準適合度がまだ高い／置換コストが大きい | 核の改造が増え続けると破綻 |
| B. 段階的にパッケージ縮小（ストラングラー） | 改造が多く、升级が苦痛 | 二重運用期間が長い |
| C. 置換（別 SaaS／自前） | パッケージが事業差別化の足かせ | 初期投資と移行リスク大 |

**方針上の既定**: まず **A でパイロット**し、改造密度と痛み（M1・M2）を見て B／C を再評価する。

## 6. 共通の設計原則

優先度の高い順。衝突したら上を優先する。

| # | 原則 | 意味 |
|---|---|---|
| P1 | **コスパ優先** | 同等の価値なら安い方。高い選択には根拠を求める |
| P2 | **段階移行** | Big Bang を避ける。スライス単位で出す |
| P3 | **学ぶために切る** | 全体理解より、小さく切って実測する |
| P4 | **一時的な共有は明示** | 共有 DB・パッケージ直結は移行期の例外。期限と解消条件を書く |
| P5 | **横に増やせる形** | ステートレス寄り。状態はマネージドへ |
| P6 | **観測できること** | レイテンシ・エラー・飽和・コストが見えること |
| P7 | **Oracle はデフォルト残さない** | 残すなら ADR で根拠。なければ寄せない |

## 7. 移行戦略（調査を薄く、実装で学ぶ）

```text
Phase 0 最低限調査（M1〜M6 のみ）
    → Phase 1 土台の最小形（クラウドに載せる・戻せる）
    → Phase 2 パイロット（パッケージ外の薄皮 1 本）
    → Phase 3 学びの横展開（同じ型で次のスライス／脱 Oracle）
    → Phase 4 パッケージ核の縮小 or 置換の再判断
```

| フェーズ | 目的 | 完了の目安 |
|---|---|---|
| 0 | パイロット可否を決める | M1〜M6 が「粗い答え」で埋まる |
| 1 | 安全に出せる置き場 | パイロットを出せて、切り戻せる |
| 2 | 型の証明 | 1 サービスが本番相当で回る |
| 3 | 型の再利用 | 2 本目以降が同じ型で速く出る |
| 4 | パッケージ戦略の再評価 | A／B／C を実データで選び直す |

### パイロットの切り方（パッケージありの場合）

優先して探すもの:

1. **パッケージ標準の外側**にある、または外に出せる機能  
2. **改造が濃いが、核マスタと疎**な周辺  
3. **読み取り中心**で、書き込み一貫性の要求が弱いもの  

避けるもの（最初は）:

- パッケージ升级のたびに必ず触る核  
- 巨大バッチとオンラインが同一トランザクションで絡む核  
- 「業務をパッケージに無理合わせ」している中心業務そのもの  

### 当面やらないこと

- 全システム As-Is の網羅ドキュメント化  
- 全チャンクのサービス分割図の完成  
- Exadata 相当のクラウド再現  
- 根拠なしの全面パッケージ置換宣言  

---

## 8. データ／Oracle 方針（最低限版）

- 新規の外側サービス: 非 Oracle を第一候補  
- パッケージ核が Oracle 必須なら、**核だけ残置**を許容（期限と根拠付き）  
- 全スキーマ移行計画は Phase 2 成功後でよい  

残置ゲート（変わらず）: 移行コスト優位／代替不可機能／規制・契約。定量で示せなければ残置承認しない。

---

## 9. コスト原則

1. 総コスト（ライセンス＋インフラ＋改造・運用の人）で見る  
2. **パッケージ改造の人件費**を見落とさない（見えにくい本命コスト）  
3. パイロットで実測してから拡大する  
4. 「分析に使う時間」もコスト。全体分析は原則しない
