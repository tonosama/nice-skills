## 1. 目的

次の転換を、コストを抑えつつ段階的に進める。

1. **実行基盤**: オンプレ → クラウド
2. **アプリ構造**: チャンク型 → マイクロサービス＋軽量な横展開
3. **データ基盤**: Oracle Exadata 依存 → 段階的に脱 Oracle（残す理由は都度検証）

方針の役割は「今すぐ全部決める」ことではない。  
**決めること／後で決めること／調べてから決めること**を分け、迷ったときの判断軸を共有することである。

---

## 2. 現状認識（仮説・未検証）

| 認識 | 確度 | 調査で確認すること |
|---|---|---|
| オンプレ中心で運用している | 高（合意済み） | 構成図、依存システム、運用体制 |
| 「チャンク型」で分割されている | 中（用語未定義） | 分割の単位（機能／バッチ／データ）と境界 |
| Exadata 上の Oracle が中核 | 高（合意済み） | スキーマ数、PL/SQL・RAC 等への依存度 |
| スケールは縦が主で、横展開が重い | 低（推測） | ボトルネック（CPU／I/O／ロック／バッチ窓） |
| Oracle を残す明確なメリットは未整理 | 高（合意済み） | 残す場合の定量メリット（性能・機能・移行コスト） |

詳細な確認項目は [discovery-checklist.md](./discovery-checklist.md) を使う。

## 3. 目標アーキテクチャ（方向性）

### 3.1 目指す姿

- **サービス境界**: 業務能力（capability）単位。デプロイ・スケール・失敗を独立させられること
- **スケール**: ステートレス寄りアプリを水平スケール。状態はマネージドサービス側へ寄せる
- **データ**: サービスごとのデータ所有を原則。共有 DB を「一時的な移行負債」として明示管理する
- **クラウド**: マネージドを優先し、自前運用（特に DB アプライアンス相当）を減らす

### 3.2 まだ決めないこと（調査後）

- [ ] クラウドプロバイダ（AWS / Azure / GCP / OCI 等）
- [ ] オーケストレーション（例: マネージド Kubernetes / コンテナサービス / PaaS）
- [ ] 最終的な主要 DB エンジン（PostgreSQL 等）と Oracle 残存範囲
- [ ] サービス分割の第一候補一覧と優先順位

## 4. 設計原則

優先度の高い順。衝突したら上を優先する。

| # | 原則 | 意味 |
|---|---|---|
| P1 | **コスパ優先** | 同等の価値なら安い方。高い選択には定量根拠（性能・リスク・人件費含む）を求める |
| P2 | **段階移行** | Big Bang を避ける。スライス単位で本番に出す |
| P3 | **境界を先に、技術を後に** | まず業務・データ境界。フレームワークや製品選定はその後 |
| P4 | **一時的な共有は明示** | 共有 DB・共有バッチは「移行期の例外」。期限と解消条件を書く |
| P5 | **横に増やせる形** | セッション・ファイル・ローカル状態に依存しない設計を既定にする |
| P6 | **観測できること** | レイテンシ・エラー・飽和・コストがサービス単位で見えること |
| P7 | **Oracle はデフォルト残さない** | 残す場合は「なぜ今は移せないか」を ADR で残す |

## 5. 移行戦略

### 5.1 フェーズ概要

```text
Phase 0 調査・可視化
    → Phase 1 基盤の土台（クラウド・CI/CD・観測・認証の最小形）
    → Phase 2 パイロットサービス（小さく切って横展開）
    → Phase 3 データ移行の本流（段階的脱 Oracle）
    → Phase 4 チャンク／巨大依存の解消と最適化
```

| フェーズ | 目的 | 完了の目安 |
|---|---|---|
| 0 調査 | 現状と負債を地図化する | チェックリストの必須項目が埋まる |
| 1 土台 | クラウドに「載せる場所」を作る | パイロットを安全に出せる |
| 2 パイロット | マイクロサービス＋横展開の型を証明する | 1〜2 サービスが本番相当で回る |
| 3 データ本流 | Exadata 依存を計画的に減らす | 主要トランザクションが非 Exadata 側へ移る |
| 4 最適化 | 残件整理とコスト最適化 | 共有負債に期限が付き、コストが追跡可能 |

### 5.2 スライスの切り方（推奨）

1. **読み取りが多い・変更が少ない**領域から切る  
2. **バッチ窓やピーク**が独立している領域を次に切る  
3. **強い一貫性が必要な核**は後回し（ストラングラーで包む）

### 5.3 やらないこと（当面）

- 全サービスの同時書き換え
- 根拠なしの「全部 Kubernetes」「全部イベント駆動」
- Exadata 相当をクラウドでそのまま再現すること（コスパ原則に反しやすい）

## 6. データ／Oracle 方針

### 6.1 方針

- **原則**: 新規機能・新規サービスは非 Oracle（候補は調査後に確定。例: PostgreSQL）を第一候補とする
- **既存**: 依存度と移行コストで優先順位を付け、段階移管する
- **残置**: 「残す」はゴールではなく、期限付きの例外とする

### 6.2 Oracle を残す場合に必要な根拠（必須）

次のいずれかが定量で示せないなら、残置を承認しない（方針上のゲート）。

1. 移行コスト（工数・リスク）が、ライセンス＋運用差分より明らかに大きい  
2. 代替 DB では満たせない必須機能／性能要件がある  
3. 規制・契約上、当面変更できない  

根拠は ADR（Architecture Decision Record）に残す。

### 6.3 移行期のパターン（候補）

| パターン | 使うとき | 注意 |
|---|---|---|
| 読み取りオフロード | 参照系を先に移す | 同期遅延の許容を決める |
| デュアルライト | 書き込みを新旧に並行 | 期間を短く。整合チェック必須 |
| ストラングラー | 入口だけ新、核は旧 | 共有 DB を負債として明示 |
| バッチ先移行 | バッチ単位で切れるとき | オンラインとの整合に注意 |

どれを主戦術にするかは Phase 0 の結果で選ぶ。

## 7. コスト原則

1. **総コストで見る**: ライセンス＋インフラ＋人の運用負荷  
2. **単位経済を持つ**: 例）リクエスト単価、バッチ 1 実行あたり、環境月額  
3. **パイロットで実測**: 見積もりだけで大規模コミットしない  
4. **アイドルを減らす**: 横展開モデルでは「止まれる／縮める」を設計に含める  
5. **比較表を残す**: Oracle 残置 vs 移行の比較は、感情ではなく表で決める
