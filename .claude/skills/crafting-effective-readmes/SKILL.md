# 効果的な README の作り方

## 概要

README は読者が持つ疑問に答える。読者が違えば必要な情報も違う — OSS のコントリビューターと、将来の自分が設定フォルダを開く場合では文脈が異なる。

**常に確認:** 誰が読み、何を知る必要があるか？

## プロセス

### ステップ 1: タスクの特定

**質問:** 「どの README 作業をしていますか？」

| タスク | タイミング |
|------|------|
| **作成** | 新規プロジェクトで README がまだない |
| **追加** | 新しく文書化するものがある |
| **更新** | 機能が変わり内容が古い |
| **レビュー** | README がまだ正確か確認 |

### ステップ 2: タスク別の質問

**初期 README 作成:**

1. プロジェクトタイプは？（下記 Project Types）
2. 一言でどんな問題を解くか？
3. 「動いた」までの最短経路は？
4. 強調したい特筆事項は？

**セクション追加:**

1. 何を文書化するか？
2. 既存構成のどこに置くか？
3. 誰が最も必要とするか？

**既存内容の更新:**

1. 何が変わったか？
2. 現行 README を読み、古い箇所を特定
3. 具体的な編集案を提示

**レビュー／リフレッシュ:**

1. 現行 README を読む
2. 実プロジェクト状態と照合（package.json、主要ファイル等）
3. 古いセクションを指摘
4. 「最終レビュー日」があれば更新

### ステップ 3: 常に確認

下書き後に質問: **「見落としている強調点や追記はありますか？」**

## プロジェクトタイプ

| タイプ | 読者 | 主要セクション | テンプレート |
|------|----------|--------------|----------|
| **Open Source** | 世界中のコントリビューター・ユーザー | Install, Usage, Contributing, License | `templates/oss.md` |
| **Personal** | 未来の自分、ポートフォリオ閲覧者 | 何をするか、Tech stack、学び | `templates/personal.md` |
| **Internal** | チームメイト、新入社員 | Setup, Architecture, Runbooks | `templates/internal.md` |
| **Config** | 未来の自分（混乱時） | 何があるか、なぜ、拡張方法、Gotchas | `templates/xdg-config.md` |

不明なら**ユーザーに確認**。すべてに OSS 既定を当てはめない。

## 必須セクション（全タイプ）

すべての README に最低限:

1. **Name** — 自明なタイトル
2. **Description** — 何を・なぜ（1–2 文）
3. **Usage** — 使い方（例があると良い）

## アンチパターン

| 避けること | 理由 | 代わりに |
|-------|-----|---------|
| 曖昧・古い手順 | 誤解を招きセットアップが摩擦になる | `package.json` と一致するコマンドを維持 |
| 空のプレースホルダーセクション | 未完成に見える | TBD セクションは削除 |
| 汎用チュートリアル | トークンを無駄にする | 具体的なインストール手順を説明 |

## 参照とテンプレート

**必須 — 読込トリガー**:

- ユーザーがプロジェクトタイプを確認したら、**必ず**対応テンプレート（`templates/internal.md` や `templates/oss.md` 等）を読む。
- 編集・整形の前に [style-guide.md](references/style-guide.md) を**必ず**読み、よくある表現の誤りを確認する。
- 単純な設定用 README では外部テンプレートや参照を**読み込まない**。
