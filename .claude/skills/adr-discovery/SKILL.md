# ADR発見 - アーキテクチャ的重要性の特定

このスキルは、エージェントとチームが技術的な決定がアーキテクチャ決定（AD）のレベルに達し、アーキテクチャ決定記録（ADR）での正式な文書化が必要かどうかを判断するのを支援します。

## プログレッシブディスクロージャーと外部リソース

- **外部リソース**: これは自己完結型のスキルです。外部ランタイムスクリプトは不要です。すべてのルールとスキーマをプロンプトコンテキスト内に保持してください。
- **参考**: 詳細については、[adr.github.io/ad-practices/](https://adr.github.io/ad-practices/)のAD慣行ホームページを参照してください。

## 自由度のキャリブレーションと制約

- **制約レベル: 中**
  - **高い厳格さ**: ASRの特定は標準的なカテゴリ分類（例：品質属性、制約、技術的負債）に厳密に従う必要があります。高リスクコンポーネントに影響する変更に「ADRを作成しない」ことを決める場合は明示的な正当化が必要です。
  - **高い自由度**: アーキテクチャへの影響の正確なスコアリングと評価は、特定のプロジェクトのサイズとテックスタックに合わせて調整できます。

## 決定ツリー：適切なアプローチの選択

```
設計/コード変更の提案
 ├─ コアな品質属性（パフォーマンス、セキュリティ、信頼性）を変更する → [ASRトリガー：ADR評価を実行]
 ├─ 新しいコアライブラリ、フレームワーク、または外部サービスを導入する → [高影響：ADRが必要]
 ├─ API、プロトコル、またはデータスキーマの契約を定義/変更する → [高影響：ADRが必要]
 └─ 既存アーキテクチャ内のローカルリファクタリングまたはバグ修正 → [低影響：延期/ADR不要]
```

## プロフェッショナルな考え方とデザイン原則

1. **「なぜ」に焦点を当てる**: コードは*何が*構築されたかを示す。Gitの歴史は*いつ*を示す。ADRは*なぜ*（アーキテクチャの根拠）と検討されたトレードオフをキャプチャする必要があります。
2. **ASR駆動の意思決定**: 決定は真空の中では行われません。1つ以上のアーキテクチャ的に重要な要件（ASR）に対処する必要があります。
3. **不変性とトレーサビリティ**: 承認されたら、決定は不変の記録です。将来の変更はそれらに取って代わります。編集しません。

## ステップバイステップの実行手順

### ステップ1：決定入力の分析

- 設計提案、イシューの説明、またはgit diffを検査する。
- 導入、変更、または廃止されるコアテクノロジー、パターン、または依存関係を特定する。

### ステップ2：アーキテクチャ的重要性指標（ASR）に対する評価

以下の基準のいずれかに決定が影響するかチェックする：

- **品質属性（非機能要件）**: システムのパフォーマンス、スケーラビリティ、セキュリティ、コスト、または保守性のプロファイルを変更するか？
- **制約**: 新しい組織的制約、コンプライアンス要件、または言語/フレームワークの制限を導入するか？
- **スコープと境界**: コンポーネントの通信方法を変更したり、ネットワークトポロジーを変更したり、外部システムに公開されるAPI/データモデルを定義したりするか？
- **可逆性コスト**: 6ヶ月後にこの決定を取り消すのはどれほど高価、複雑、または時間がかかるか？（高い場合はADRが必要）

### ステップ3：アクションと次のステップの推奨

- **アーキテクチャ的に重要な場合**: `adr-authoring`スキルを使用して新しいADRの草稿作成を推奨する。
- **上書きする場合**: 置き換えられる既存のADRを特定し、`adr-lifecycle-management`スキルのためにメモする。
- **重要でない場合**: 完全なADRを作成せずに、PRの説明やイシューコメントに根拠を簡潔に文書化する。
- 標準化されたキャプチャスクリプトを使用してローカルメモリキャプチャをトリガーする。

## 重要なアンチパターン（NEVERリスト）

| アンチパターン | 説明 | 代替/解決策 |
| :--- | :--- | :--- |
| **サイレントアーキテクチャクリープを無視してはいけない** | 軽微な変更が積み重なってADRなしでシステムトポロジーを変更することを許す。 | コアAPIまたはインフラに触れる設計提案やPRに対してこの評価を実行する。 |
| **シンプルなコードスタイルにADRを書いてはいけない** | 些細なフォーマット、変数名、またはマイクロ最適化のためにADRを作成する。 | 長期的な高可逆性コストを持つ決定にのみADRを制限する。 |
| **全員が「なぜ」を知っていると仮定してはいけない** | 現在のチームが口頭で合意しているためADRを省略する。 | 将来のチームメンバーと外部ステークホルダーのために記録を書く。 |

## 一般的なエラーシナリオとフォールバック

### シナリオ1：アーキテクチャへの影響の曖昧さ

- **根本原因**: 変更が複雑であるか要件が曖昧であり、可逆性コストを判断しにくい。
- **フォールバック**:
  1. インタラクティブな`/grill-me`セッションをトリガーして制約とオプションを明確にする。
  2. 軽量なリスク分析を実行する（影響と失敗の可能性）。
  3. チームが未決定のままであれば、デフォルトで軽量ADR（例：MADRフォーマット）を作成する。
