# コミット作業

## 目標

レビューしやすく安全にリリースできるコミットを作る:

- 意図した変更だけを含める
- コミットは論理的な単位で分ける（必要なら分割）
- コミットメッセージは何がどう変わり、なぜかを説明する

## 不足時に確認する入力

- 単一コミットか複数コミットか？（不明なら、無関係な変更が混ざっている場合は小さな複数コミットをデフォルトとする）
- コミット形式: Conventional Commits を必須とする
- その他のルール: subject の最大長、必須 scope など

## ワークフロー（チェックリスト）

1) ステージ前に作業ツリーを確認

   - `git status`
   - `git diff`（未ステージ）
   - 変更が多い場合: `git diff --stat`

2) コミット境界を決める（必要なら分割）

   - 分割の目安: feature vs refactor、backend vs frontend、フォーマット vs ロジック、テスト vs 本番コード、依存バンプ vs 挙動変更
   - 1 ファイルに変更が混在する場合は patch ステージを検討

3) 次のコミットに属するものだけステージ

   - 混在変更は patch ステージを優先: `git add -p`
   - hunk / ファイルの unstage: `git restore --staged -p` または `git restore --staged <path>`

4) 実際にコミットされる内容をレビュー

   - `git diff --cached`
   - 確認事項:
     - secret やトークンがないこと
     - 意図しない debug ログがないこと
     - 無関係なフォーマット変更がないこと

5) ステージ済み変更を 1〜2 文で説明（メッセージ作成前）

   - 「何が変わったか？」＋「なぜか？」
   - きれいに説明できない場合、コミットが大きすぎるか混在している可能性がある → 手順 2 に戻る

6) コミットメッセージを書く

   - Conventional Commits（必須）:
     - `type(scope): short summary`
     - 空行
     - 本文（what/why。実装日記にしない）
     - 必要なら footer（BREAKING CHANGE）
   - 複数行はエディタ推奨: `git commit -v`
   - 参考: `references/commit-message-template.md`

7) 最小限の関連検証を実行

   - リポジトリで最速かつ意味のあるチェック（unit test、lint、build など）を次に進む前に実行

8) 作業ツリーがクリーンになるまで次のコミットを繰り返す

## 成果物

適切にステージ・メッセージ付けされた 1 件以上の git コミット。

## アンチパターンと安全上の注意

| 避けること | 理由 | 代わりに |
|-------|-----|---------|
| 曖昧なコミットメッセージ | 文脈が失われ変更追跡が困難 | 明確な what/why を書く |
| 未完成コードのコミット | ビルド破壊・ノイズ | `git stash` や一時ブランチで保存 |
| 未解決のコンフlict マーカー | `<<<<<<<` のコミットでコード破損 | ステージ前に検索確認 |
| 誤った secret の混入 | 認証情報漏洩リスク | コミット前にステージ行をスキャン |
| 生のコミット一覧の羅列 | 暗号化された出力、文脈無視 | 人が読める要約で成果を説明 |

### Git リカバリと検証失敗

コミット直後にコンパイルやテストが失敗した場合:

```bash
git reset HEAD~1
```

コード編集は保持したまま、変更を unstaged に戻す。

## 参照とテンプレート

- **必須**: 複数段落メッセージの複雑な feature をステージする場合、[commit-message-template.md](references/commit-message-template.md) のレイアウトガイドを **必ず** 読む
- **読み込まない**: 標準的な短い bugfix メッセージのみの場合は外部コミットガイドを読み込まない
