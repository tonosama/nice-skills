# ADR作成 - 根拠を持った決定の草稿作成

このスキルは、エージェントとチームが業界標準のテンプレートと構造を使用して、コンテキスト、明確なトレードオフ、および下流への影響を強調した高品質なアーキテクチャ決定記録（ADR）を作成するのを支援します。

## プログレッシブディスクロージャーと外部リソース

- **外部リソース**: これは自己完結型のスキルです。テンプレートはインラインで説明されています。外部スクリプトは不要です。
- **参考**: 詳細については、[adr.github.io/adr-templates/](https://adr.github.io/adr-templates/)のテンプレートリストを参照してください。

## 自由度のキャリブレーションと制約

- **制約レベル: 中**
  - **高い厳格さ**: すべての草稿ADRには3つの基本セクションが含まれている必要があります：コンテキスト、決定（ステータス付き）、結果（トレードオフ、新しいリスク、必要な更新）。
  - **高い自由度**: テンプレート形式の選択（NygardかMADRかYステートメントか）はチームの好みやプロジェクトの慣例に委ねられています。

## 決定ツリー：適切なテンプレートの選択

```
対象者と深度の決定
 ├─ 軽量、開発者向け、マークダウンネイティブ → [MADRテンプレートを使用]
 ├─ 業界標準、シンプル、ナラティブ構造 → [Nygardテンプレートを使用]
 ├─ フォーマル、エンタープライズグレード、高度に構造化、理由ベース → [Yステートメントテンプレートを使用]
 └─ アジャイル、簡潔、最小限のオーバーヘッド → [軽量パラグラフテンプレートを使用]
```

## プロフェッショナルな考え方とデザイン原則

1. **根拠よりも結果**: 決定の影響（何を可能にし、無効にし、強制し、制限するか）は、なぜ選ばれたかよりも重要です。
2. **正直なトレードオフ**: すべての設計上の選択にはデメリットがあります。ADRでネガティブを文書化することを拒否するのはアンチパターンです。
3. **遡及的な書き換えなし**: ADRは短く、客観的で、同時代のものにしてください。決定が下されたときに書いてください。

## ステップバイステップの実行手順

### ステップ1：ADRテンプレートの選択

決定要件を確認し、テンプレートスタイルを選択します：

#### オプションA：Nygardテンプレート（クラシック）
```markdown
# [番号]. [タイトル]

## ステータス
[Draft | Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-XX]

## コンテキスト
[解決しようとしているコンテキストと問題は何か？制約は何か？]

## 決定
[コミットする変更/決定は何か？]

## 結果
[何が容易になり、何が難しくなるか？どんな新しい問題が発生するか？影響は何か？]
```

#### オプションB：MADRテンプレート（Markdown ADR）
```markdown
# [決定記録のタイトル]

* Status: [draft | proposed | accepted | rejected | deprecated | superseded by [ADR-XX](file:///path/to/adr-XX.md)]
* Deciders: [名前のリスト]
* Date: [YYYY-MM-DD]

## Technical Story
* [ストーリー/エピック/イシューへのリンク]

## コンテキストと問題の説明
[コンテキストと問題を説明する。例：自由なテキストや質問のセットとして。]

## 決定ドライバー
* [ドライバー1、例：パフォーマンス]
* [ドライバー2、例：コスト]

## 検討したオプション
* [オプション1]
* [オプション2]

## 決定結果
選択したオプション：[オプションX]、なぜなら[正当化]。

### ポジティブな結果
* [例：速度が向上する]

### ネガティブな結果
* [例：運用コストが増加する]

## オプションの長所と短所

### [オプション1]
* 良い点、なぜなら[論拠]
* 悪い点、なぜなら[論拠]
```

#### オプションC：Yステートメントテンプレート
```
[ユースケース/コンテキスト]のコンテキストにおいて、
[選択したオプション]を決定し、
[代替オプション]に反対し、
[品質属性/ドライバー]を達成するために、
[結果/デメリット]を受け入れます。
```

### ステップ2：コンテキストとトレードオフの収集

- 技術的なドライバーを質問/討議する（例：パフォーマンス、コスト、複雑さ、ベンダーロックイン）。
- 現実的に検討された代替オプションをリストアップする。
- 各オプションの長所と短所を定義する。

### ステップ3：記録の執筆とレビュー

- 選択したテンプレートに記入する。
- ファイル名は標準的な命名パターンに従う：`docs/adr/NNNN-title-in-kebab-case.md`（例：`docs/adr/0004-use-postgres-for-caching.md`）。
- 結果セクションに実行可能なアイテム（例：チームトレーニング、マイグレーションスクリプト、ドキュメント更新）が含まれているか検証する。
- 標準化されたキャプチャスクリプトを使用してローカルメモリキャプチャをトリガーする。

## 重要なアンチパターン（NEVERリスト）

| アンチパターン | 説明 | 代替/解決策 |
| :--- | :--- | :--- |
| **ネガティブを隠してはいけない** | ネガティブな結果を省略したり、解決策にデメリットがないふりをする。 | ネガティブな結果/トレードオフの文書化に同等の努力を注ぐ。 |
| **ブログ記事を書いてはいけない** | 簡潔な構造化された記録の代わりに長い散漫なエッセイを書く。 | ADRは短く保つ（最大1〜2ページ）。箇条書きを使用する。 |
| **ステータスを追跡しなくなってはいけない** | ステータスを設定することを忘れ、何がアクティブかについて混乱を招く。 | ファイルの先頭にStatusセクションを明確に更新して配置する。 |

## 一般的なエラーシナリオとフォールバック

### シナリオ1：トレードオフに関するコンセンサスの欠如

- **根本原因**: チームメンバーが検討したオプションの長所/短所について意見が分かれている。
- **フォールバック**:
  1. 「長所と短所」セクションにすべての異なる意見を正直に文書化する。
  2. オーナー/リードアーキテクトに最終的な決定結果を下してもらう。
  3. ステータスを「Proposed」に変更し、集合的なレビューのためにPRを開く。
