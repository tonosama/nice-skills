# Feedback Conversations

## Overview

職場での難しい会話と効果的なフィードバックのためのフレームワークを提供する。パフォーマンス問題、コンフリクト解消、建設的フィードバックのいずれでも、構造化アプローチがより良い結果につながる。

**要点:** 研究では、準備と明確なフレームワークで難しい会話に臨んだ従業員は、計画なしで臨む場合より**正の解決に至る確率が約 60% 高い**。

## このスキルを使うとき

- 同僚や直属部下へフィードバックを伝える準備をするとき
- パフォーマンス問題や期待未達に対処するとき
- チームメンバー間のコンフリクトを扱うとき
- センシティブな 1:1 を行うとき
- フィードバックを受け、建設的に応答したいとき
- ステークホルダーとの期待調整をするとき

**キーワード**: feedback、difficult conversation、1:1、performance、conflict、expectations、behavior、confrontation

## Core Frameworks

### Preparation-Delivery-Follow-up Model

難しい会話の 3 部構成:

| フェーズ | 焦点 | 主要な問い |
| --- | --- | --- |
| **Preparation** | 問題理解、目標定義、感情管理 | 問題は何か？望む結果は？落ち着いているか？ |
| **Delivery** | 中立的に開始、事実ベース、対話を促す | どう始める？根拠は？どう巻き込む？ |
| **Follow-up** | 合意の記録、チェックイン、支援 | 何に合意した？いつ再確認？どう支援する？ |

### SBI Feedback Model

**Situation-Behavior-Impact（SBI）** で具体的・客観的・実行可能なフィードバックを構成:

| 要素 | 説明 | 例 |
| --- | --- | --- |
| **Situation** | 具体的状況 | 「昨日の code review で…」 |
| **Behavior** | 観察可能な行動（解釈ではない） | 「…Sarah の説明中に 3 回割り込んだ…」 |
| **Impact** | チーム／プロジェクト／個人への影響 | 「…彼女が意見を言いにくくなり、議論が遅れた。」 |

**効く理由:** SBI は仮定を除き観察可能な事実に焦点を当て、防御反応を減らす。

## Preparation Phase

### Step 1: Understand the Issue

自問する:

- **問題の正体は？**（曖昧にしない）
- **チーム・プロジェクト・会社への影響は？**
- **関連事実は揃ったか？**
- **パターンか一度きりか？**

### Step 2: Define Your Goals

会話前に求めるものを明確化:

| 目標タイプ | 例 |
| --- | --- |
| 行動変化 | 「code review を期限内に出してほしい」 |
| 相互理解 | 「何が妨げているか理解したい」 |
| 期待の設定 | 「機能の『完了』の定義を揃えたい」 |
| 問題解決 | 「一緒に解決策を見つけたい」 |

**ヒント:** if-then で利害を明確化:
> 「この行動が続くと、プロジェクト日程が崩れ、納期を逃す。」

### Step 3: Manage Your Emotions

感情が高ぶると認知処理は約 30% 低下。会話前に:

- [ ] 冷静で制御できているか
- [ ] 事実と個人的苛立ちを分離したか
- [ ] 相手の視点を考えたか
- [ ] 非難なしに伝えられるか

**リフレーミング:**

| 非難的 | 建設的 |
| --- | --- |
| 「いつも期限を逃して皆を遅らせる」 | 「最近遅れが見える。直面している課題を聞きたい」 |
| 「ちゃんとテストしない」 | 「バグがいくつか抜けた。何が起きたか、どう改善できるか話したい」 |

## Delivery Phase

### The Three-Step Delivery Formula

1. **中立と意図で始める**
2. **非難ではなく事実で問題を示す**
3. **対話と解決策を促す**

### Opening Lines That Work

| 文脈 | オープニング |
| --- | --- |
| 一般 | 「チームの成功に重要なことを話したい。あなたの視点も聞きたい。」 |
| パフォーマンス | 「いくつかパターンがある。批判ではなく支援が目的だ。」 |
| コンフリクト | 「緊張があるかもしれない。あなた側で何が起きているか理解したい。」 |
| 期待 | 「期待を揃えたい。このプロジェクトの進み方を一緒に確認できる？」 |

### Facts, Not Blame

| 非難 | 事実 |
| --- | --- |
| 「このプロジェクトに本気じゃない」 | 「直近 3 回のミーティングで更新が短かった。負荷に何かある？」 |
| 「品質を気にしていない」 | 「この PR で QA が 12 件キャッチした。何が起きたか改善策を話そう」 |
| 「いつも遅刻」 | 「スタンドアップは 9:00 開始で、直近 3 日 9:15 参加。状況は？」 |

**原則:**

- 一般化（「always」「never」）ではなく具体例
- 動機の推測ではなく観察可能な行動
- 人格ではなく影響に焦点

### Encouraging Dialogue

観察を述べたら協働へ:

| 状況 | 対話プロンプト |
| --- | --- |
| 障壁の理解 | 「何が難しかった？」 |
| 相手の見方 | 「あなたはどう見ている？」 |
| 解決策 | 「成功に何が役立つ？」 |
| 認識の一致 | 「これはあなたの理解と合っている？」 |

## Follow-up Phase

うまくいってもフォローで持続的変化を作る。

### Follow-up Checklist

- [ ] **合意したアクションを記録** — 具体的に何が変わるか
- [ ] **チェックイン日を設定**
- [ ] **継続支援** — どう助けるか
- [ ] **進捗を認める** — 改善があれば称える

### Sample Follow-up Message

```markdown
Hi [Name],

Thanks for the conversation yesterday. I appreciated your openness.

**What we agreed to:**
- [Action item 1] - [Timeline]
- [Action item 2] - [Timeline]

**Check-in:** Let's reconnect [date] to see how things are going.

I'm here if you need any support. Thanks for working through this with me.

Best,
[Your name]
```

## SBI Examples for Software Teams

### Positive Feedback

**Code Review:**
> **Situation:** "During Tuesday's code review for the authentication module..."
> **Behavior:** "...you provided detailed comments on potential security vulnerabilities and suggested efficient fixes..."
> **Impact:** "...which strengthened our security posture and saved the team hours of debugging later."

**Collaboration:**
> **Situation:** "In yesterday's architecture discussion..."
> **Behavior:** "...you asked clarifying questions and built on others' ideas instead of pushing your own solution..."
> **Impact:** "...which helped us reach consensus faster and made everyone feel heard."

### Constructive Feedback

**Missed Deadlines:**
> **Situation:** "When we were finalizing the API deployment last Thursday..."
> **Behavior:** "...your testing results came in two hours after our agreed cutoff..."
> **Impact:** "...which delayed the release, risked our SLA, and caused the QA team to work overtime."

**Meeting Behavior:**
> **Situation:** "In our sprint planning yesterday..."
> **Behavior:** "...you were on your phone for most of the discussion and didn't contribute when we asked for estimates..."
> **Impact:** "...which left the team without your expertise on the backend stories and made others feel their time wasn't valued."

## Common Difficult Scenarios

### Scenario: Performance Issue

**状況:** 開発者が継続的にバグの多いコードを出す。

**アプローチ:**

1. **Prepare:** 具体例（PR、バグ数、タイムライン）を集める
2. **Deliver:** 「直近 Y PR で X 件のバグ。何が起きているか、どう支援できるか知りたい。」
3. **Explore:** 負荷、要件の明確さ、テスト自信を聞く
4. **Collaborate:** 「品質に自信を持つには何が必要？」
5. **Follow-up:** 合意した変更後に確認し、改善を認める

### Scenario: Conflict Between Team Members

**状況:** 2 人のエンジニアが技術方針で争い、チームに影響。

**アプローチ:**

1. **まず個別に:** それぞれの視点を理解
2. **共通点:** 両者の望み（動くプロダクト、良いコード等）
3. **共同でファシリテート:** 人格ではなく事実とトレードオフ
4. **決定プロセス:** 意見不一致時のチームの決め方
5. **Follow-up:** 解決策が機能しているか確認

### Scenario: Unrealistic Expectations

**状況:** 経営が必要時間の半分で機能を求める。

**アプローチ:**

1. **Prepare:** 類似過去作業のデータ、タスク分解
2. **Deliver:** 「現実的な線を揃えたい。こう見えている…」
3. **トレードオフ:** 「その日付ならスコープ削減／人員追加／リスク受容」
4. **Collaborate:** 「最優先は日付かフル機能か？」
5. **文書化:** 書面合意で将来のズレを防ぐ

**詳細スクリプト:** `references/difficult-conversation-scripts.md`

## Receiving Feedback Well

受け手として:

### During the Conversation

1. **最後まで聞く** — 反論の準備をしながら聞かない
2. **明確化の質問** — 「具体例は？」
3. **言い換えで確認** — 「つまり…ということ？」
4. **影響を認める** — 意図が違っても「そう受け取られた」と認める
5. **防御しない** — 指摘に感謝

### After the Conversation

1. **正直に内省** — 真実の部分はあるか
2. **アクション** — 何を変えるか
3. **フォローアップ** — 変更内容を伝える
4. **継続フィードバックを求める** — 成長へのコミットを示す

## Anti-Patterns

| 避けること | 理由 | 代わりに |
|-------|-----|---------|
| 一般化（「always」「never」） | 即座に防御反応 | 具体的な事実と状況パラメータ |
| 公開でのフィードバック | 公開の恥・信頼破壊 | 重要フィードバックは非公開 1:1 |
| フィードバックの重複 | エスカレーション経路の混乱 | 複雑なパフォーマンス計画は `difficult-workplace-conversations` を参照 |
